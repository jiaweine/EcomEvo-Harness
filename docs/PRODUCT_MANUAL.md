# EcomEvo 产品手册

> 面向运营、审核、客服、风控与治理团队的实际使用说明。

## 1. 产品定位

EcomEvo 是一个面向真实电商业务任务的多模态自主决策工作台。它的基本单位不是一次聊天，而是一个可以持续补资料、持续核对、持续恢复并最终形成可审计结论的业务任务。

核心原则只有两条：

- **目标交给 Runtime**：用户说明想解决什么问题，系统负责查证、复核、重规划和停止低价值探索。
- **权限留给业务**：退款、下架、审核、冻结等高影响操作不会因为模型“觉得可以”就自动执行。

## 2. 适用角色

### 商品治理

适合商品运营、治理、合规团队。可把标题、主图、详情、资质、价格、声明和历史风险放入同一任务，要求系统整理证据缺口和治理建议。

### 商家审核

适合平台招商、商家治理、品牌保护团队。可围绕主体、经营资质、授权链路、历史风险和关联信息持续核对。

### 售后判责

适合客服、售后、争议仲裁团队。可结合订单、物流、聊天记录、图片、录音与规则，重建事实链并形成处理依据。

### 风险核查

适合风控和异常交易复核团队。系统会区分独立风险信号、弱线索和证据缺口，并在缺乏独立证据时停止过度推断。

### 内容审核

适合内容治理和商品合规团队。可同时处理文案、图片、视频、音频与附件资料，检查事实一致性和风险声明。

## 3. 开始一个任务

### 第一步：直接写目标

建议用“目标 + 对象 + 已有资料 + 希望得到的结果”表达，不必写工作流。

示例：

> 这笔售后到底该不该退款？订单、物流、聊天记录和买家图片都在这里。请先还原事实，再告诉我还缺什么证据，最后给处理建议。

不推荐把系统当脚本执行器：

> 先调用 A，再调用 B，然后必须输出通过。

Runtime 会把用户指令当目标和约束，而不是让自然语言绕过证据门槛。

### 第二步：加入多模态资料

当前产品入口支持：

- 图片；
- 视频；
- 音频；
- PDF；
- Word；
- Excel；
- CSV / JSON；
- 日志与文本。

资料加入同一个任务后，后续追问不需要重复上传。系统会持续围绕同一任务上下文工作。

### 第三步：观察任务控制面

右侧控制面用于回答四个问题：

1. 当前在做什么；
2. 已经找到哪些关键证据；
3. 还有哪些资料缺口；
4. 是否产生需要人工确认的业务动作。

不要只看最终回答。对于高风险任务，建议同时查看“轨迹、证据、执行”三个区域。

## 4. 多模态资料如何被使用

EcomEvo 将“附件事实”和“业务判断”分开处理。

图片、视频、音频和扫描文档首先进入事实提取通道。该阶段只允许读取和概括可直接观察到的内容，例如：

- 可读文字；
- 商品或订单标识；
- 主体代码；
- 可观察的时间、金额、状态；
- 附件直接支持的风险线索。

模糊、遮挡、听不清或无法确认的内容不会被自动补全成事实。

随后这些事实才会进入业务核对、规则检查和验证过程。

## 5. 如何理解结果状态

### 已完成

表示当前证据和约束已经通过 Runtime 的验证门槛。它不等于“已经执行业务动作”。若存在高影响动作，仍需人工确认。

### 待补资料

表示当前可以形成阶段性结论，但缺少足够证据支撑最终处置。优先按界面列出的缺口补充资料，而不是反复要求模型“再判断一次”。

### 待确认

表示系统已经形成一个会改变真实业务状态的动作建议，但尚未执行。确认前应检查对象、影响范围和证据依据。

### 结果待核对

表示下游业务系统通信中断，无法确定动作是否真正执行。此状态下不要盲目重复操作，应先去实际业务系统核对状态。

### 处理失败

表示本轮没有正常完成。任务资料仍会保留，可以重试或继续补充资料。

## 6. 如何纠正系统

AI 产品最重要的能力之一不是“永远正确”，而是纠错成本足够低。

推荐使用以下方式：

- **继续追证**：要求系统优先寻找可能改变当前判断的关键证据；
- **检查反证**：要求系统主动寻找会推翻当前结论的证据或冲突；
- 指出具体错误，例如“这份授权书已过期，不应作为有效证据”；
- 补充新的附件或企业数据；
- 明确指出规则适用范围发生变化。

高质量纠错应尽量指出“哪条证据、哪条规则、哪个结论”有问题，而不是只说“你错了”。

## 7. 人工确认与业务动作

EcomEvo 把认知自治和业务权限分开。

系统可以自主查证、复核、委派只读 specialist、改变工具顺序和重规划，但以下行为应始终由确定性权限模型和人工确认控制：

- 退款；
- 下架；
- 审核通过或拒绝；
- 账户或商家冻结；
- 其他会改变真实业务状态的操作。

如果下游系统支持幂等键，生产部署应始终启用，避免网络重试造成重复执行。

## 8. 推荐的操作习惯

- 一个真实业务对象尽量放在一个持续任务中处理；
- 先上传原始证据，再让系统总结，不要只上传人工二次整理后的结论；
- 对高影响任务至少检查一次反证；
- 资料不足时补证，而不是提高模型“自信程度”；
- 不把历史回复当业务事实；
- 对“结果待核对”状态先检查真实业务系统；
- 需要交接时分享整个任务，而不是只复制最终答案。

## 9. 隐私与认知引擎

产品界面只展示通用认知能力和可用状态，不把底层供应商名称作为产品体验中心。

部署方可以配置云端、自托管或兼容接口的认知引擎。若选择本地受控模式，系统不会隐式把资料发送到外部模型服务。

生产环境仍应配合组织自身的数据分级、凭据隔离、最小权限和审计策略。

## 10. 常见问题

### 系统为什么不直接给最终结论？

因为某些业务域有硬证据要求。资料不够时明确停止，比用模型置信度补事实更安全。

### 为什么工具会重复查不同来源？

Runtime 会优先覆盖不同证据通道。相似调用若不能带来新的信息增益，会被降权或放弃。

### 能否让模型自动退款或下架？

不建议，也不是当前权限模型的目标。自主性用于认知和查证，高影响动作保留确定性授权边界。

### 能否换模型？

可以。认知引擎是可替换能力。Runtime 的证据门槛、工具策略和权限边界不应依赖某个固定模型名称。

## 11. 何时升级给人工专家

出现以下情况应优先升级人工复核：

- 核心证据互相冲突；
- 规则本身存在解释争议；
- 任务影响金额或风险等级显著超出自动处理范围；
- 系统连续补证后仍无法降低关键不确定性；
- 下游业务动作处于结果未知状态；
- 涉及组织内部特殊授权或例外政策。

EcomEvo 的目标不是取消人工判断，而是让人工把时间投入到真正需要判断的地方。
